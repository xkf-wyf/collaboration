# R001 · 范围澄清

## 一、先说结论：这句话现在无法开工

「数据开发及数据问题处理」是一个**业务领域**，不是一条**可执行需求**。

区别很具体：可执行需求能回答"做完之后什么东西变了、怎么验证"。这句话回答不了——它可以是 20 种不同的东西，从一份 SOP 文档到一个连库跑校验的工具，工作量差两个数量级。

如果现在就把它转给 CodeBuddy，它只有两个选择：要么反问（浪费一轮），要么自己挑一个理解开始写（**这最危险**——它挑了你不想要的那个，等你看到产出才发现方向错了，前面的活全废）。

所以本轮的正确产出不是代码，是**范围收敛**。

## 二、把一个领域拆成可判断的候选

### 数据开发（造数据）

| 子领域 | 典型任务 | 可自动化程度 |
|--------|----------|--------------|
| 建表与 DDL | 分层建表、字段规范、分区策略 | 高（模板化） |
| ETL/ELT 逻辑 | 增量/全量/拉链、去重、口径实现 | 中（需业务口径输入） |
| 调度与依赖 | 任务编排、依赖配置、重跑策略 | 中低（平台耦合强） |
| 数据迁移 | 如 MySQL → Paimon/Hive 的结构与数据搬迁 | 中（校验是关键） |

### 数据问题处理（救数据）

| 问题类型 | 典型现象 | 排查确定性 |
|----------|----------|-----------|
| 产出异常 | 任务失败、延迟、未产出 | 高（有日志） |
| 量级异常 | 行数突增突降、分区为空 | 高（可量化） |
| 质量异常 | 主键重复、空值率超标、枚举越界 | 高（规则可枚举） |
| 口径异常 | 指标对不上、报表与底表不一致 | 低（需业务确认定义） |
| 血缘异常 | 上游变更导致下游静默出错 | 中（需血缘信息） |

**观察**：越往下，自动化收益越低、需要人判断的比例越高。而**质量异常和量级异常**这两类，规则明确、可枚举、可自动生成 SQL——是最适合先做的一块。

## 三、三种落地形态，代价差很大

| 形态 | 是什么 | 依赖 | 适用 |
|------|--------|------|------|
| **A. 资产库** | SOP 文档 + SQL 脚本库 + 模板，人和 agent 都能取用 | 无（纯文件） | 立刻可做，零环境依赖 |
| **B. 自动工具** | 连库执行校验 SQL，自动出体检报告 | 数据库连接权限、驱动 | 收益最大，但卡在权限 |
| **C. 逐单代工** | 不建工具，每天的任务直接进流水线，我分析、CodeBuddy 产 SQL | 无 | 见效最快，但不成体系 |

三者不互斥：A 是地基，B 是 A 的自动化，C 是用 A 和 B 干活的方式。

## 四、我目前不知道、且不能替你决定的事

1. **数据环境到底是什么** —— MySQL？Hive？Paimon？Doris？还是混合？不同方言的 SQL 不通用。
2. **能不能连库** —— 只读权限有没有？如果不能连，B 形态直接出局。
3. **你真正的痛点在造还是在救** —— 是"开发太慢"还是"数据老出问题"？两者的 P0 完全不同。
4. **交付给谁用** —— 只有你自己用，还是要给团队？
5. **「1、」后面还有什么** —— 如果是并列的几点，应当一起看再定优先级，否则容易做重复的东西。

## 五、我的建议

先做 **A + C 组合**，不碰 B：

- **A 提供地基**：把「数据问题处理」的排查路径固化成可复用资产（每类问题的判断顺序、要跑的 SQL、结论怎么记）
- **C 验证价值**：拿你手上一个**真实的历史问题**跑一遍，看这套东西能不能真的缩短排查时间

理由：B 形态听起来最爽，但它要求数据库权限、要处理方言差异、要防误操作，任何一项没谈好就卡死。而 A + C 零依赖，**一周内就能验证这套协作到底值不值得继续投入**。如果跑通了，再把常用 SQL 抽成 B，那时你已经有真实样本，不会白写。
