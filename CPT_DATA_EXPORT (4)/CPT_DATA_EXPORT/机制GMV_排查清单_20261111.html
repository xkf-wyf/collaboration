一、先纠正一个前提：这段校验没在核对机制GMV接口

校验 cell 3 的 t1 子查询，读的不是机制GMV表，而是二级总销售表：

-- 校验脚本 cell 3（t1 = 接口侧）
from ${spark.var.catalog.ads}.fin_cpt.ads_second_total_sales_mf
where dt = '$dt' and abs(secondary_gmv_amount) > 0
  and sales_type = '2C'

而机制GMV接口是 fin_cpt.ads_secondary_gsv_gmv_mf。两张表的加工链路完全不同：

二级总销售
←
dws.ddm.dws_trd_total_item_sales_df（item 粒度）
机制GMV
←
dws_trd_total_sku_sales_df（sku 粒度）
+
猫超 ods_tm_market_trd_sku_sales_day_di
+
VIP dwd_vip_trd_barcode_sales_df

结论 「43.59 亿 vs 45.69 亿」本质是 item 粒度源表 vs sku 粒度源表 的差异， 不是「机制GMV 算错 2.1 亿」。要校验机制GMV 接口本身，t1 必须换成 ads_secondary_gsv_gmv_mf —— 见第四节 F1。

四、验证 SQL（按此顺序执行）

F1　最高优先 用对表，把「机制GMV 接口」本身放进漏斗

把 4 个环节的金额串起来，一眼看出机制GMV 在哪一步丢数。这张结果决定后面所有判断。

with a as (select round(sum(secondary_gmv_amount),2) v, count(*) c
           from ${spark.var.catalog.ads}.fin_cpt.ads_secondary_gsv_gmv_mf
           where dt = '$dt' and left(month,4) = '2026'),
     b as (select round(sum(secondary_gmv_amount),2) v, count(*) c
           from ${spark.var.catalog.ads}.fin_cpt.ads_second_total_sales_mf
           where dt = '$dt' and left(month,4) = '2026' and sales_type = '2C'),
     c as (select round(sum(gmv),2) v, count(*) c
           from ${spark.var.catalog.tmp}.fin.tmp_trd_total_item_sales_all where abs(gmv) > 0),
     d as (select round(sum(gmv),2) v, count(*) c
           from ${spark.var.catalog.tmp}.fin.tmp_trd_total_item_sales_all
           where abs(gmv) > 0 and flag = 1 and nvl(sku_code,'') <> '')
select '1 机制GMV接口落表' as seg, v, c from a
union all select '2 二级总销售接口', v, c from b
union all select '3 机制中间表全量', v, c from c
union all select '4 中间表 flag=1 且 sku_code 非空', v, c from d
order by seg;

读法：③ − ④ = 被 flag=1 / sku_code 两个过滤条件砍掉的量； ④ − ① = 加工过程的其它损耗（bu 白名单、组套 lp_contri 归零等）。 若 ① 与 ② 差 2.1 亿而 ① 与 ④ 接近，则「机制GMV 接口本身没问题，是校验拿错了表」。

F2　猫超 定位 TMALL SUPER 的 40% 丢在哪一步

select '猫超源表-已匹配店铺' as seg
     , count(*) as cnt, round(sum(gmv),2) as gmv
from ${spark.var.catalog.tmp}.fin.tmp_trd_total_item_sales_tm_supper_data
where customer is not null
union all
select '猫超源表-shop_id未匹配', count(*), round(sum(gmv),2)
from ${spark.var.catalog.tmp}.fin.tmp_trd_total_item_sales_tm_supper_data
where customer is null
union all
select '进入汇总(platform=TMALL SUPER)', count(*), round(sum(gmv),2)
from ${spark.var.catalog.tmp}.fin.tmp_trd_total_item_sales_all
where platform = 'TMALL SUPER'
union all
select 'flag=1 保留', count(*), round(sum(gmv),2)
from ${spark.var.catalog.tmp}.fin.tmp_trd_total_item_sales_all
where platform = 'TMALL SUPER' and flag = 1
union all
select '落表(store_name=TMALL SUPER)', count(*), round(sum(secondary_gmv_amount),2)
from ${spark.var.catalog.ads}.fin_cpt.ads_secondary_gsv_gmv_mf
where dt = '$dt' and left(month,4) = '2026'
  and store_name = 'TMALL SUPER';

判定：若第 1 行就明显小于 4.60 亿 → 猫超 ods 源覆盖不足（DDM 侧提单）； 若第 3 行够、第 4 行锐减 → 打标表 dim_sku_pack_size 或 dim_prd_sku 未覆盖猫超商品（CPT 侧可修）。

F3　打标 TMALL SUPER 的品线组为何 54.5% 为空

select case when b.sku_code is null  then '① 价格表无此 sku_code'
            when b.national_ex42 is null then '② 有 sku 但 national_ex42 为空'
            else '③ 已打标' end as seg
     , count(distinct a.sku_code) as sku_cnt
     , round(sum(a.gmv),2) as gmv
from ${spark.var.catalog.tmp}.fin.tmp_trd_total_item_sales_all a
left join (select sku_code, national_ex42
           from ${spark.var.catalog.dim}.cd.dim_product where is_current = 1) b
       on a.sku_code = b.sku_code
where a.platform = 'TMALL SUPER' and abs(a.gmv) > 0
group by 1 order by gmv desc;

五、校验脚本自身的 3 个缺陷

序号缺陷证据影响量级
① 接口侧基准表错 cell 3 的 t1 读 ads_second_total_sales_mf，不是机制GMV的 ads_secondary_gsv_gmv_mf。 两条链路源表不同（item 粒度 vs sku 粒度 + 3 个特例源），差异不可归因于机制GMV接口。 全量口径
② full join 的 NULL 陷阱 join 条件含 t1.product_line_group = t2.product_line_group 等 5 个等值。两侧同为 NULL 时 NULL = NULL 返回 unknown，同一组数据被拆成「接口有 / 源有」两行，各行 gap 被放大。 逐行 gap 合计 −2.625 亿，真实总额差 −2.095 亿，虚增 0.53 亿。 虚增 5,298 万
③ 0 值行被过滤后仍参与 join t1 有 abs(secondary_gmv_amount) > 0，t2 有 abs(gmv) > 0， 两侧都为 0 的键不会出现在结果里；但单侧为 0 时会被当成「凭空多/少」计入 gap。 叠加在 ② 上

补充：校验 t2 侧已经做了 JD - REGENERATE → JD - UL 归并（cell 3，注释 20260907）， 与接口第 832 行的归并口径一致 —— 这一点 GMV 侧是对的。另有 $store 白名单里 没有 'JD - REGENERATE'，但因已归并，不影响结果。

六、结论与建议动作

结论说明动作
−2.10 亿不是机制GMV 的错 88% 来自 TMALL SUPER、8% 来自 VIP - UL，两者都是「机制链路换了源表」导致的覆盖差； 其余 22 个店差异率 0.0%–0.8%，链路加工本身是准的。 先把 F1 跑出来，确认 ①≈④
TMALL SUPER 是唯一需要提单的 猫超改走 ods_tm_market_trd_sku_sales_day_di 后只覆盖源侧 60%， 且 54.5% 的 GMV 打不上品线组。这是 DDM / 上游数据供给问题。 F2 定位到具体环节后向 DDM 提单
VIP - UL 属历史口径差 1–7 月稳定 −38%，8 月自动对齐至 0.8%。不需修数据，但需在校验里注明 「202608 前 VIP 不参与对数」。 校验脚本加白名单/说明
PDD 是归类差，不是多算 二级总销售只拆 PDD - VSL，没拆 PDD - AHC / DTC，导致 +4029 万落在 PDD - UL。 机制链路按 dim_store 全量归类，口径更细。 在二级总销售补 DTC 拆分，或校验时合并 PDD 系
JD 202606 需单独看 10 个月里 9 个月精确为 0，仅该月 −2180 万。典型单日数据事件。 F4 逐日排查该月

执行顺序建议

  1. F1（一次查询，4 行结果）—— 判断「机制GMV 接口本身是否漏数」，决定后续方向
  2. 若 F1 显示 ①≈④ → 本接口无问题，问题在校验基准表，直接改校验 cell 3 的 t1
  3. 若 ① 远小于 ④ → F2 定位猫超丢在哪一步（源覆盖 or 打标）
  4. F3 并行跑，量化品线组打标缺口归属哪一侧
  5. F4 收尾单点异常月（JD 202606 / VIP 202609-202610）

全部 SQL 跑在 fin_cpt / tmp / dim 上，不触碰 dws 层。 ${spark.var.catalog.tmp}.fin.tmp_* 系列是接口最后一次运行的中间结果，与 dt=2026-11-10 的落表同批。
